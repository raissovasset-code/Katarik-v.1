# Поддержка, диагностика и восстановление «Катарика»

Документ предназначен для разбора обращений игроков и production-инцидентов.
Адрес production: `https://katarik-5g25.onrender.com`.

## 1. Что запросить у игрока

Для первого разбора достаточно:

- времени сбоя с часовым поясом;
- платформы: браузер и ОС либо версия Android;
- режима игры и количества игроков;
- кода комнаты, если комната еще существует;
- последнего действия перед ошибкой и текста ошибки;
- скриншота или короткой записи экрана;
- информации, повторяется ли сбой после обычного переподключения.

Нельзя просить или публиковать:

- `sessionToken`;
- содержимое `localStorage` или `sessionStorage`;
- полный WebSocket-трафик активной комнаты;
- чужие карты или персональные данные игроков.

Открытый GitHub issue подходит только для несекретных сведений. Если игрок готов
потерять возможность вернуться на прежнее место, локальные данные можно очистить
последним шагом диагностики, но не первым.

## 2. Приоритет инцидента

| Уровень | Пример                                                                                | Действие                                                                 |
| ------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| P1      | Игра недоступна всем, `/api/ready` не готов, есть риск потери комнат или безопасности | Остановить новые релизы, начать диагностику и восстановление немедленно  |
| P2      | Массово не работают создание, вход, ходы или один игровой режим                       | Проверить production, собрать затронутые комнаты, исправить или откатить |
| P3      | Ошибка одного устройства, визуальный дефект или понятный обходной путь                | Воспроизвести, зарегистрировать и исправить обычным релизом              |

Если обращение указывает на утечку токена, чужие карты или обход прав хозяина,
его следует считать инцидентом безопасности и не обсуждать секретные детали в
публичном issue.

## 3. Быстрая проверка production

### Процесс сервера

```powershell
Invoke-RestMethod https://katarik-5g25.onrender.com/api/health |
  ConvertTo-Json -Depth 4
```

Нормальный ответ: HTTP `200`, `status: "ok"`. Поле `roomStorage` в production
должно быть `redis`, а не `memory`.

### Redis и WebSocket

```powershell
Invoke-RestMethod https://katarik-5g25.onrender.com/api/ready |
  ConvertTo-Json -Depth 4
```

Нормальный ответ: HTTP `200`, `status: "ready"`,
`checks.roomStorage: true` и `checks.websocket: true`.

### Настоящий WebSocket `ping/pong`

```powershell
$env:NODE_OPTIONS = "--use-system-ca"
npm run monitor:production --prefix server
```

Команда проверяет `/api/ready`, открывает
`wss://katarik-5g25.onrender.com` и ожидает `pong`. Успешный результат содержит
`"status":"ready"`. Параметр `--use-system-ca` нужен Windows-версии Node, если
без него появляется `UNABLE_TO_VERIFY_LEAF_SIGNATURE`; он действует только в
текущем окне PowerShell.

Workflow `Production Monitor` выполняет ту же проверку автоматически каждые три
часа и вручную через GitHub Actions. При сбое он создает или обновляет issue
`[monitor] Production server unavailable`, а после восстановления закрывает его.

## 4. Как читать результат

| Health               | Ready                       | WebSocket monitor | Вероятная область сбоя                                            |
| -------------------- | --------------------------- | ----------------- | ----------------------------------------------------------------- |
| Не отвечает/не `200` | —                           | —                 | Процесс Render не запущен, идет деплой или сервис недоступен      |
| `200`                | `503`, `roomStorage: false` | Ошибка            | Redis/`REDIS_URL` или связь web service с Key Value               |
| `200`                | `503`, `websocket: false`   | Ошибка            | HTTP-сервер поднят, WebSocket еще не готов                        |
| `200`                | `200`                       | Ошибка            | WebSocket-прокси, сеть, TLS или несовместимый ответ               |
| `200`                | `200`                       | Успех             | Сервис исправен; искать проблему комнаты, клиента или сети игрока |

Во время бесплатного cold start первая проверка может быть медленной. Перед
эскалацией повторить проверку один раз после полного запуска сервиса.

## 5. Структурированные логи

Логи web service в Render состоят из JSON-строк:

```json
{
  "timestamp": "2026-07-26T12:00:00.000Z",
  "level": "info",
  "event": "room_created",
  "roomId": "ABC123",
  "mode": "classic",
  "players": 1
}
```

Полезные события:

| Событие                                               | Значение                                                           |
| ----------------------------------------------------- | ------------------------------------------------------------------ |
| `server_started`                                      | процесс начал принимать запросы                                    |
| `rooms_restored`                                      | комнаты восстановлены из Redis после запуска                       |
| `volatile_room_storage`                               | сервер стартовал без Redis; для production это ошибка конфигурации |
| `room_created`, `player_joined`, `player_reconnected` | жизненный цикл комнаты работает                                    |
| `room_deleted`, `rooms_expired`                       | комнаты удалены штатно                                             |
| `redis_error`                                         | ошибка клиента Redis                                               |
| `persisted_room_invalid`                              | одна сохраненная комната повреждена и пропущена при загрузке       |
| `room_cleanup_failed`                                 | не выполнена фоновая очистка                                       |
| `disconnected_room_persist_failed`                    | состояние комнаты не сохранилось после обрыва                      |
| `bot_turn_failed`                                     | серверный бот не смог завершить ход                                |

Для поиска инцидента сначала фильтровать по времени, затем по `event` и
`roomId`. При массовом сбое сравнить время ошибки с последним Render deploy и
workflow GitHub Actions.

Прикладной logger намеренно не записывает имена, карты, токены, payload и
IP-адреса. Не добавлять эти данные в логи вручную.

## 6. Восстановление

### Сбой только у одного игрока

1. Проверить, что production monitor успешен.
2. Попросить переключить сеть или перезапустить приложение/вкладку.
3. Повторить вход по тому же коду комнаты: сохраненные идентификатор и токен
   позволяют вернуть прежнее место.
4. Только если прежнее место больше не нужно, выйти из комнаты или очистить
   локальные данные приложения.

### Перезапуск web service

Если код исправен, но процесс завис или не завершил запуск:

1. Зафиксировать время и состояние health/ready.
2. Проверить последние логи и статус Render.
3. Перезапустить только web service `katarik`.
4. Убедиться, что появился `rooms_restored` со `storage: "redis"`.
5. Проверить ready, WebSocket monitor и переподключение к существующей комнате.

Комнаты хранятся в `katarik-rooms` и должны пережить перезапуск web service.
Нельзя отключать `REDIS_URL` ради временного запуска в памяти: новые комнаты не
переживут следующий рестарт.

### Сбой Redis

1. Проверить состояние Key Value `katarik-rooms` в Render.
2. Проверить привязку `REDIS_URL` и отсутствие недавнего изменения конфигурации.
3. Восстановить доступность Redis, не создавая параллельное пустое production-
   хранилище.
4. Перезапустить web service при необходимости.
5. Подтвердить `roomStorage: "redis"` и `checks.roomStorage: true`.

Если лог содержит `persisted_room_invalid`, поврежденная комната пропускается, а
остальные продолжают загружаться. Ручное удаление ключа допустимо только после
проверки точного кода комнаты и понимания, что эта партия не восстановится.

### Ошибка нового релиза

Если инцидент начался после deploy и не устраняется конфигурацией, выполнить
безопасный `git revert` по
[процедуре staging и отката](RELEASE_ROLLBACK.md). Не переписывать историю
`main` через `reset --hard` или force push.

## 7. Проверка после восстановления

Инцидент можно закрывать, когда:

1. `/api/health` и `/api/ready` стабильно отвечают `200`;
2. production monitor с системным хранилищем сертификатов успешен;
3. создается новая комната и второй клиент входит в нее;
4. при необходимости проверено переподключение к существующей комнате;
5. GitHub `Project CI`, `Browser E2E` и `Staging Release Check` зеленые для
   исправления или отката;
6. issue монитора закрыт автоматической проверкой либо содержит итог ручной
   проверки.

## 8. Запись результата

В issue инцидента сохранить:

- начало и конец сбоя в UTC;
- влияние на игроков и известные коды затронутых комнат;
- причину;
- commit/deploy, который вызвал и который устранил проблему;
- выполненные проверки;
- дальнейшее действие, предотвращающее повторение.

Не копировать в отчет секреты, полные игровые состояния или карты игроков.

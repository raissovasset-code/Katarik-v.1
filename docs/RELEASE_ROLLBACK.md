# Staging и откат релиза

## Staging-проверка

Workflow `Staging Release Check` поднимает временное изолированное окружение:

- собирает production-версию клиента;
- запускает сервер с отдельным Redis;
- ожидает успешный ответ `/api/ready`;
- проверяет настоящий WebSocket `ping/pong`;
- при ошибке сохраняет серверный лог на семь дней.

Workflow запускается для pull request в `main`, при изменении самой staging-конфигурации и вручную через GitHub Actions. Временное окружение удаляется после проверки и не расходует ресурсы Render.

Перед выпуском рискованного изменения нужно убедиться, что зелёные:

1. `Project CI`;
2. `Browser E2E`;
3. `Staging Release Check`;
4. `Production Monitor` после выкладки.

## Когда нужен откат

Откат выполняется, если после выпуска:

- `/api/ready` возвращает не `200`;
- перестал работать WebSocket;
- появилась массовая ошибка создания, входа или восстановления комнат;
- новый сервер не может читать существующие комнаты из Redis.

## Безопасная процедура отката

1. Остановить новые изменения в `main`.
2. Найти последний исправный commit по зелёным workflow.
3. Определить commit или последовательность commit, вызвавших сбой.
4. Создать ветку с префиксом `codex/rollback-`.
5. Выполнить `git revert` проблемных commit. Не использовать `git reset --hard` и не переписывать историю `main`.
6. Отправить ветку и дождаться успешных `Project CI`, `Browser E2E` и `Staging Release Check`.
7. Влить откат в `main`. Render автоматически развернёт новый commit.
8. Проверить `/api/ready`, WebSocket и вход в существующую комнату.
9. Убедиться, что `Production Monitor` снова зелёный, и закрыть связанный инцидент.

Пример отката одного commit:

```powershell
git switch -c codex/rollback-YYYYMMDD
git revert <problem-commit-sha>
git push -u origin codex/rollback-YYYYMMDD
```

Если проблема вызвана только настройками Render или Redis, код откатывать не нужно. Сначала следует вернуть последнюю рабочую конфигурацию сервиса, затем повторно проверить readiness и WebSocket.
